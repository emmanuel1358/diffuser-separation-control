## 1. Shared grader / shared pipeline

### S1 — `grade_problem` returns a clean `0.0` when `extra_fields.test_file` is absent

**Severity:** warning on #119, but it is the *mechanical cause* of the
`golden_score 0.0` / `invalid_golden_solution` probes on #118 and #119.
**Where:** `taiga_runtime/rubric/src/rubric/server.py:1481-1487`

```1481:1487:taiga_runtime/rubric/src/rubric/server.py
    test_file = fields.get("test_file")
    if not test_file:
        return Grade(
            subscores={"score": 0.0},
            weights={"score": 1.0},
            metadata={"error": "missing test_file"},
        )
```

A missing `test_file` is always a caller/configuration fault, never an agent
fault, yet this path leaves `env_internal_failure` unset. Every downstream
monitoring/regrade lane that omits `test_file` records an indistinguishable
legitimate zero. Note that every *other* failure path in the same file already
uses `_failure_grade(..., env_internal_failure=True)`
(`server.py:1195-1210`, `:1366`, `:1405`, `:1425`, `:1436`, `:1446`).

**Fix**

```python
    test_file = fields.get("test_file")
    if not test_file:
        message = "grade_problem called without extra_fields.test_file"
        return _failure_grade(
            {"error": message},
            message,
            env_internal_failure=True,
            env_internal_failure_logs=[message],
        )
```

Add a regression test in `harness/tests/` asserting
`grade_problem(problem_id, transcript, extra_fields={})` sets
`env_internal_failure is True`. This is a two-line change with the highest
signal-to-effort ratio of anything in this document — it clears one warning
directly and de-noises the two golden-solution probes on the other PRs.

Also mirror the change into `lbx-rl-tasks-iso-mothership` (identical file, same
line numbers) and `lbx-rl-tasks-iso-template-xfoil-pr` (`:1412-1418`).

### S2 — No golden-solution artifact ever ships to Taiga

**Severity:** `critical` on #118 (`env_linter`), contributory on #119.
**Where:** `alignerr_plugin/src/alignerr_plugin/exporters/taiga.py:35-38, 422-456, 670-672`

The exporter is explicitly designed to ship only a *redacted proof summary*:

> **Redacted ground-truth evidence.** … It never ships raw solution files,
> hidden fixtures, trajectories, or scorer metadata.

So `extra_fields.ground_truth_evidence` claims `expected_score: 1.0` while the
problem-version record carries no `golden_patch` and the image contains no
`solution/`, no `.alignerr/build_proof.json`. Taiga's golden probe therefore
grades an untouched `/tmp/output` and records `0.0` — a permanent contradiction
between our claimed contract (`task.toml [ground_truth] in_container = true`,
`score_epsilon = 0.001`) and what the platform can observe.

This is a design decision that now has a cost. Three options, in order of
preference:

1. **Ship the oracle as a root-only in-image artifact and register it.** Bake
   `solution/` into the image at `/mcp_server/golden` (mode `0700 root`, same
   protection as `/mcp_server/grader`), and add a `golden_command` to the Taiga
   problem entry so the platform's golden lane runs it instead of staging an
   empty workspace. This preserves secrecy (uid-1000 agent cannot read
   `/mcp_server`) while making `in_container = true` true.
2. **Ship `golden_patch`** with the oracle output artifact only (not the search
   code) — for all three tasks the deliverable is a small JSON/XML file. Lower
   effort, but it leaks the answer to anyone with problem-version read access.
3. **Stop claiming an in-container ground truth** when we do not ship one: have
   the exporter omit `ground_truth_evidence.expected_score` unless a golden
   artifact is actually included, and set `in_container = false`. This clears
   the critical honestly but loses the oracle-solvability signal.

Recommend option 1, gated behind a new exporter check that raises at submit time
if `[ground_truth] in_container = true` and no golden artifact was collected.

### S3 — An artifact-level `AgentFault` zeroes the entire rubric, including the file/parse gate rows

**Severity:** two `warning`s on #118 (one `env_linter`, one `reward_hacking`).
**Where:** `grader/src/grading/evaluation/rubric.py:340` and
`grader/src/grading/evaluation/artifacts.py:168-173`

```336:343:grader/src/grading/evaluation/rubric.py
        except (OSError, ValueError) as exc:
            raise AgentFault(f"could not commit submitted artifact: {exc}") from exc

        candidate = self.artifact.load(workspace)
        fixtures = {
            name: fixture.load(private) for name, fixture in self.fixtures.items()
        }
```

`self.artifact.load(workspace)` runs *before* the criteria are constructed, so
any `AgentFault` it raises — unexpected key, missing key, out-of-range numeric,
non-UTF-8 — propagates out of `grade()`, is caught by the runner
(`server.py:634-642`), and collapses to a scalar `0.0` with
`return_shape: agent_fault`. A submission with all four correct
`hydrofoil_flap.json` fields plus a `"note"` key loses even the
`output_exists` (0.003) and `json_parses` (0.004) rows it demonstrably earned.

The declarative surface already knows which rows are structural gates
(`RubricCriterion(required=True)`). The framework should honour that instead of
throwing everything away.

**Fix:** in `RubricTask.grade`, wrap the artifact load and, on `AgentFault`,
return a Grade whose *gate* criteria are scored from what was actually
observable and whose remaining criteria are `0.0`, with
`headline_score_override=0.0` and the fault string in metadata. Concretely:

```python
        try:
            candidate = self.artifact.load(workspace)
        except AgentFault as exc:
            return self._artifact_rejection(exc, evaluation_context, workspace)
```

where `_artifact_rejection` mirrors `_unclassified_failure` but keeps the
declared criterion ids (so Boreal still renders the rubric table) and records
which stage failed (`exists` / `parses` / `schema` / `numeric`). Even if the
headline stays 0.0, the finding is about *diagnosability and calibration
honesty*, and the per-row breakdown is what QA is asking for.

**Paired problem-side fix:** see P10 — `allow_extra_keys=False` must be stated
in the prompt, or relaxed.

**Severity:** `info` `problem_linter` on all three PRs.
**Where:** `alignerr_plugin/src/alignerr_plugin/exporters/taiga.py:235-238, 292-301`

`required_tools` does not include `tmux` (mujoco-pendulum declares neither).

### S5 — Prompt-referenced deliverable filename is not in `preloaded_files`

**Severity:** `critical` `data_quality` on **both** #118 and #119.

> Prompt references `['isolation_design.json']`; payload has 7 files.
> Prompt references `['hydrofoil_flap.json']`; payload has 5 files.

Taiga's `data_quality` check extracts file *basenames* from `task_prompt` and
asserts each is present in `preloaded_files`. Our deliverable lives under
`output_directory` (`/tmp/output`), so it can never be in the payload. Evidence
that it is basename-based, not literal-token-based: openfoam's prompt only ever
writes the path form `/tmp/output/hydrofoil_flap.json`, yet the bare name was
still reported. Evidence it only fires when a payload exists: mujoco-pendulum
ships an empty `data/` (no `preloaded_files` field) and was **not** flagged.

This is a shared exporter/prompt-contract problem — it will fire on every future
task that has both `/data` inputs and a named deliverable.

**Fix, in order:**

1. **Confirm the rule against live Taiga docs before coding.** Check whether
   `data_quality` already excludes `output_directory` / `outputs[].path`
   basenames, and if not, file it — we already send both `output_directory` and
   `outputs` in the problem entry (`taiga.py:765, 781-783`), so the platform has
   everything it needs to exclude them.
2. **Interim, per-task:** ship a starter file in `/data` whose basename is
   exactly the deliverable. opensees already has `isolation_starter.json` (a
   deliberately poor too-soft design) and openfoam has
   `hydrofoil_flap_template.json` — renaming/duplicating these to
   `isolation_design.json` and `hydrofoil_flap.json` satisfies the check with no
   semantic loss, and both graders already cap the score for a verbatim
   template copy (openfoam) or score it near zero (opensees).
3. **Add a pre-submit lint** in the exporter that cross-checks prompt basenames
   against `preloaded_files ∪ {outputs basenames}` and fails loudly, so this is
   caught before a Taiga job burns.

### S6 — Base-image gaps (both #117 criticals)

**Where:** `base/install-common.sh`, `base/cpu/Dockerfile`

#### S6a — `pip` is a dangling symlink in the runtime venv

```170:170:base/install-common.sh
ln -sf "${RUNTIME_VENV_DIR}/bin/pip" /usr/local/bin/pip
```

`uv venv` (line 89) does not install `pip` into the venv, so
`/opt/lbx-runtime/.venv/bin/pip` never exists and `/usr/local/bin/pip` is a
broken link. `python3 -m pip` returns "No module named pip". The only working
`pip3` on PATH belongs to the `python:3.13-slim` system CPython at
`/usr/local`, whose site-packages the venv cannot see. Agents waste turns here
and misdiagnose the environment — in run `1bc6cb61` the model concluded "No
MuJoCo or numpy yet" and re-installed packages that were already present.

**Fix:** either bootstrap pip into the venv

```bash
uv pip install --python "${RUNTIME_VENV_DIR}/bin/python" --no-cache pip
```

or replace the symlink with a wrapper that forwards to `uv pip` against the
runtime venv (mirrors the existing `python` wrapper at lines 164-169):

```bash
cat > /usr/local/bin/pip <<'PIP_WRAPPER'
#!/bin/sh
exec /usr/local/bin/uv pip --python /opt/lbx-runtime/.venv/bin/python "$@"
PIP_WRAPPER
chmod 0755 /usr/local/bin/pip
ln -sf /usr/local/bin/pip /usr/local/bin/pip3
```

The wrapper also fixes `pip3` pointing at the wrong interpreter. Add a
`harness/tests/test_base_image.py` assertion that `pip --version` succeeds and
that `pip show mujoco` resolves inside the runtime venv.

#### S6b — No GL backend in the CPU base

`base/install-common.sh:19` installs `libgl1` only. There is no `libegl1`, no
`libosmesa6`, and no `MUJOCO_GL` default, so `mujoco.Renderer(model)` raises
`FatalError: an OpenGL platform library has not been loaded` for every backend.
4 of 5 mujoco-pendulum runs attempted offscreen rendering for self-verification
and failed. The `mlenvs-cuda-graphics` flavor already gets this right
(`base/mlenvs-cuda-graphics/Dockerfile:40-41, 56` — `libosmesa6`,
`MUJOCO_GL=osmesa`, `PYOPENGL_PLATFORM=osmesa`), and our *authoring* side can
render (the build proof ships a 1280x720 `rendering.mp4`), so this is an
authoring-vs-runtime parity gap.

**Fix:** add `libegl1 libosmesa6` to the apt list in `install-common.sh`, add
`pyopengl` to `requirements-common.txt`, and set `ENV MUJOCO_GL=osmesa` /
`PYOPENGL_PLATFORM=osmesa` in `base/cpu/Dockerfile` (matching the
cuda-graphics flavor). Extend `harness/tests/test_base_image.py` with a headless
`mujoco.Renderer` smoke test.
