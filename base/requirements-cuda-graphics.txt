# CUDA-native rasterization deps that ARE on PyPI.
#
# IMPORTANT: hardware GL/EGL is NOT deployable on Taiga's gVisor + nvproxy nodes
# (the graphics-memory ioctls are not forwarded; glBufferData returns
# GL_OUT_OF_MEMORY even on an 80GB H100). Do NOT register NVIDIA EGL/Vulkan ICDs.
# CUDA-native rasterization (nvdiffrast / pytorch3d) is the only render path that
# works under the sandbox.
#
# nvdiffrast and pytorch3d are NOT published on PyPI (verified: `pip install
# nvdiffrast` resolves to "no matching distribution"). They are installed from
# source in base/cuda-graphics/Dockerfile against the torch+CUDA the base
# provides (pytorch3d compiles CUDA extensions, which is why that base uses the
# CUDA -devel image and ninja). fvcore + iopath are pytorch3d build/runtime deps
# and DO live on PyPI.
trimesh
# pyrender is intentionally NOT installed. Every pyrender release hard-pins
# pyopengl==3.1.0, but mujoco==3.8.0 (requirements-common.txt) hard-pins
# pyopengl==3.1.7 -- a mutually exclusive exact-pin conflict. uv then walks to
# ancient pyrender (0.1.4-0.1.34), which pin an exact PRE-RELEASE pyglet
# (==1.4.0a1/b1) that uv refuses without --prerelease=allow, so the whole
# cuda-graphics resolve dead-ends. pyrender is also a GL rasterizer, and the
# header above documents that hardware GL/EGL is not deployable on Taiga's
# gVisor+nvproxy nodes; nvdiffrast/pytorch3d (CUDA-native) is the only working
# render path here, so pyrender was dead weight regardless.
imageio
imageio-ffmpeg
fvcore
iopath
# 3D / neural-rendering stack for graphics ML tasks. The PyG binaries are NOT

# open3d and kaolin are intentionally absent. open3d's latest release (0.19.0)
